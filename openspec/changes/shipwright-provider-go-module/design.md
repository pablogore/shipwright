# Design: Extract `internal/capabilities/` into a standalone `providers/go` module

## Technical Approach

Two chained PR slices with a manual git-tag interlude between them, because the
tag cannot exist before the code and the `require`+`go.sum` cannot exist before
the tag.

| Slice | Content | Resolution mechanism |
|---|---|---|
| **1** | Create `providers/go` module, `git mv` 13 files, swap all importers, add `go.work`, add 3 guard tests, delete `internal/capabilities/` | Temporary `replace ... => ./providers/go` in root `go.mod` (explicitly sanctioned by proposal D4) |
| **tag** | `git tag providers/go/v0.1.0 <slice-1 merge sha> && git push origin providers/go/v0.1.0` | — (manual task, not a PR) |
| **2** | Delete the `replace`, keep `require .../providers/go v0.1.0`, regenerate root `go.sum`, add the no-`replace` guard test, verify `go install` from a clean cache | Published, path-prefixed tag (D4 final state) |

Slice 1 is green in **both** workspace and `GOWORK=off` mode (the `replace`
covers non-workspace resolution), so the repo is never left uncompilable
between slices. The only constraint during the window: **do not cut a root
release tag**, because a root tag with a directory `replace` would not
`go install`.

## Architecture Decisions

### Decision: `go.work` content and the `.dagger` guard (D1 mechanics)

**Choice** — exact committed file, nothing else:

```
go 1.26.1

use (
	.
	./providers/go
)
```

Guard lives in the **root module** (`go.work` is a root-level file) as a new
package `internal/workspaceguard/` mirroring `internal/daggerpin/` one-for-one:
`work.go` (parse + extract helpers) + `work_test.go` (repo assertion + synthetic
fail-closed cases in `t.TempDir()`). It parses `go.work` with
`golang.org/x/mod/modfile.ParseWork` — already a direct root dependency
(`golang.org/x/mod v0.35.0`, used by `daggerpin`). Assertions:

1. The `use` set equals exactly `{".", "./providers/go"}` (allowlist — any
   addition fails, not just `.dagger`).
2. No `use` path has a cleaned segment equal to `.dagger` or `dagger`, with a
   dedicated message naming the `design.md` D-B isolation it would collapse.
3. A missing/unparseable `go.work` fails closed (`t.Fatal`), as `daggerpin`
   does for a missing `dagger.json`.

**Alternatives considered** — a comment in `go.work` (proposal already rejected);
a CI `grep` step. **Rationale** — a text/AST-style guard is the repo's
established pattern (`daggerpin`, `api_golden_test.go`): no engine, no network,
runs locally in milliseconds, and the allowlist form catches accidental
`use ./.dagger` *and* any other unreviewed workspace member.

### Decision: `providers/go` module shape (D2 mechanics)

**Choice** — `providers/go/go.mod`:

```
module github.com/pablogore/shipwright/providers/go

go 1.26.1

require (
	dagger.io/dagger v0.21.8
	github.com/pablogore/shipwright v0.0.0-<pre-extraction-commit-pseudo-version>
)
// indirect block generated by `GOWORK=off go mod tidy` (dagger's querybuilder,
// gqlgen, otel, golang.org/x/* — a strict subset of root's own indirect set)
```

`go 1.26.1` (matches root exactly, not `.dagger`'s 1.26.5 — `.dagger` is
deliberately not analogous). `dagger.io/dagger v0.21.8` copied verbatim from
root's pin; **no new `daggerpin`-equivalent package inside `providers/go`.**
Instead `internal/daggerpin/pin_test.go` gains one test,
`TestProvidersGoDaggerVersionMatchesRoot`, reusing the existing
`GoModDaggerVersion` unchanged against `providers/go/go.mod`.

*Rationale*: cross-module Dagger pin parity is already `daggerpin`'s declared
job (COMPATIBILITY.md Axis 4), `GoModDaggerVersion` already handles
replace-wins and local-path fail-closed, and this adds **zero** new production
code. `go.work` alone is insufficient — in workspace mode Go silently picks one
version via MVS, so drift would build cleanly and only diverge for external
consumers.

Package name `golang`; file layout is a strict 1:1 rename (no file renamed, no
file split):

| From | To |
|---|---|
| `internal/capabilities/{gobuilder,gounittester,golinter,govulnscanner,containerpublisher}.go` | `providers/go/<same name>.go` |
| `internal/capabilities/{…}_test.go`, `internal_test.go`, `integration_test.go`, `naming_test.go` | `providers/go/<same name>` |

### Decision: importer swap is **wider than the proposal stated** (D3 correction)

Exploration and the proposal both say "the single importer". The tree has
**three**:

| File | Change |
|---|---|
| `internal/workflow/providers/register.go` | import + 5 type references |
| `internal/app/container.go` (`BuildCapabilities`) | import + 5 type references |
| `internal/app/container_capabilities_test.go` | import + 6 type assertions |

Every one is a pure identifier/import edit. Verified against the source: all
five types are plain structs with exported fields (`Client`, `Config`,
`GoVersion`); no constructor exists, no signature changes, no field renames.
**Zero behavior change confirmed** — but slice 1's diff and the RED-test plan
must cover `internal/app`, not only `internal/workflow/providers`.

```go
- "github.com/pablogore/shipwright/internal/capabilities"
+ golang "github.com/pablogore/shipwright/providers/go"
…
- return &capabilities.GoBuilder{Client: client, Config: …}
+ return &golang.GoBuilder{Client: client, Config: …}
```

`register.go` keeps its `internal/workflow/interp` and `pkg/shipwright` imports
untouched — dependency direction stays core→provider.

Two moved files are **not** byte-identical renames and need real edits:
`naming_test.go` (hard-codes `pkgs["capabilities"]` → `pkgs["golang"]`, plus its
`internal/capabilities` doc references) and each file's package clause + package
doc comment (`Package capabilities …` → `Package golang …`, documenting the
deliberate directory/package-name mismatch that forces the import alias).

### Decision: break the module cycle by pinning **backwards in time** (D4 mechanics)

The chicken-and-egg is real: root requires `providers/go` for `RegisterDefaults`,
and `providers/go` requires root for `pkg/shipwright`. **Choice**: pin
`providers/go`'s root requirement to a *pseudo-version of the pre-extraction
commit* (slice 1's merge-base on `develop`, which already contains the frozen
`pkg/shipwright`). That commit's root `go.mod` has no `providers/go`
requirement, so the module graph is acyclic:

```
root@HEAD ──requires──▶ providers/go@v0.1.0 ──requires──▶ root@v0.0.0-…-<pre-extraction sha>
                                                                   │
                                                     (no providers/go requirement) ──▶ ∎
```

MVS then selects the main module for the root path, and no `go.mod` ever names a
version that does not yet exist. Pseudo-versions need no tag at all, and the repo
already uses one (`github.com/pablogore/kit-logger v0.1.2-0.2026…`).

**Alternatives considered** — (a) cut a root tag first so `providers/go` can
require a real root version: adds a release event to a structural change and
still leaves a true cycle in the graph; (b) require root at the *post*-extraction
version: genuine cycle, and the version does not exist when the tag is cut.
**Rationale** — (chosen) is the only ordering where each artifact only ever
references something that already exists.

**Version: `providers/go/v0.1.0`** — confirmed. `v0.x` states "no compatibility
promise while the pattern is proven", which is exactly what COMPATIBILITY.md
Axis 5 already says about provider versions ("not covered by any Shipwright
guarantee"), and `v0.x`/`v1.x` avoids the `/vN` major-suffix path rule on a path
element that is already a Go keyword.

**Tagging is manual, one-time, and a task — not automation.** `.goreleaser`
builds the root binary only; a recurring provider release process is explicitly
out of scope in the proposal. Tagging slice 1's `develop` merge commit is
deliberate: Go resolves tags regardless of branch, and the provider's version
line is independent of the root's release line (Axis 5). Consequence:
`providers/go/`'s content must be **final in slice 1** — a later correction costs
`v0.1.1`, because a published tag is immutable on the proxy (the change's one
one-way door).

### Decision: external-implementability guard = AST import scan **inside** `providers/go` (D5 mechanics)

**Choice** — `providers/go/internalimport_test.go`, `package golang_test`:
locate the module directory via `runtime.Caller(0)`, `parser.ParseDir` **including**
`_test.go` files, collect every import path, and fail naming the offending file
and import if any path has an `internal` segment.

**Decisive rationale** — *the Go compiler does not enforce this here.*
`internal/**` visibility is **path-prefix** based, not module based:
`github.com/pablogore/shipwright/providers/go` sits under
`github.com/pablogore/shipwright/`, so `import ".../internal/workflow/interp"`
from the new module **compiles fine** even across the module boundary. Without
this test the change's entire property is unenforced.

**Alternatives considered** — (b) a CI step building `providers/go` in isolation:
proves nothing extra (see above), cannot run locally, fails late and remotely,
and costs a CI stage; (c) a `go list -m all` shell assertion: needs network, and
asserts dependencies rather than imports. Both rejected.

Scanning test files too is intentional: a test reaching into `internal/**` would
mean the module is only implementable-from-outside for its production half.

## Data Flow

Package-level direction (unchanged, one-way):

    manifest ──▶ internal/workflow/providers.RegisterDefaults ──▶ providers/go (golang.*)
    internal/app.BuildCapabilities ─────────────────────────────▶ providers/go (golang.*)
                                                                        │
                                                                  pkg/shipwright
                                                                  dagger.io/dagger

Module resolution by consumer:

| Consumer | Mode | `providers/go` resolved from |
|---|---|---|
| Contributor / CI in the checkout | workspace (auto-detected) | `./providers/go` via `use` |
| `GOWORK=off go build ./...` | single-module | slice 1: `replace`; slice 2: tag `v0.1.0` |
| `go install github.com/pablogore/shipwright@<tag>` | no main module, `go.work` ignored | tag `v0.1.0` from the proxy |

**`go.work` is auto-detected** from cwd upward — a contributor who never ran
`go work init` is still in workspace mode once the file is committed. So "not
using `go.work`" means `GOWORK=off`, `go install`, or an external importer, and
all three are covered by the table above. Commit `go.work` **and** `go.work.sum`
if one is generated (Go's own recommendation for a single-repo workspace);
`go work sync` is the maintenance command.

## Interfaces / Contracts

No new interfaces. The only new contract is the package-name/import-path
mismatch, documented once in the package doc:

```go
// Package golang provides Shipwright's Go-toolchain capability
// implementations … The package name deliberately differs from the last path
// element of github.com/pablogore/shipwright/providers/go, because `go` is a
// Go keyword and `package go` is a syntax error; importers alias it:
//   import golang "github.com/pablogore/shipwright/providers/go"
package golang
```

Lint check for apply: `.golangci.yml` enables `revive` with default rules only —
`var-naming` does not flag a package-name/path mismatch (that is `stylecheck`
ST1003 / `importas`, neither enabled). Expected clean; verify with
`golangci-lint run` anyway.

## Testing Strategy

Strict TDD: every guard is RED first (the assertion exists before the artifact
it asserts), and every moved test must be seen failing in its new location
before its source file is moved.

| Layer | What to test | Approach | RED-first order |
|---|---|---|---|
| Unit | `go.work` allowlist + `.dagger` rejection + missing-file | `modfile.ParseWork` over the real file; synthetic `t.TempDir()` cases for the detector | Write `work_test.go` before `go.work` exists → fails closed |
| Unit | `providers/go` imports no `internal/**` | `parser.ParseDir` incl. `_test.go`, `runtime.Caller` self-location | Write before moving sources → fails on missing package |
| Unit | Dagger pin parity across 3 files | Extend `daggerpin` (reuses `GoModDaggerVersion`) | Write before `providers/go/go.mod` exists |
| Unit | Bundle-name golden after move | `naming_test.go` with `pkgs["golang"]` | Edit key before package clause changes → RED |
| Unit | Provider names unchanged | Existing `register_test.go` / `container_capabilities_test.go` — must stay green through the swap | Regression, not new |
| Unit (root) | Committed root `go.mod` has no `replace` | Slice 2: `modfile.Parse` + assert `len(f.Replace) == 0` | Written in slice 2 while the `replace` is still present → RED |
| Integration (`-short`-guarded) | Real-engine `GoBuilder`/`GoUnitTester` | Moved unchanged; `./...` does **not** cross into `providers/go` in workspace mode (verified empirically — see the corrected Open Question below), so `make test`/CI now run an explicit `(cd providers/go && go test ./...)` to keep this covered | Regression |
| E2E (manual) | `examples/workflow/diamond.yaml` | Run before and after; compare resolved providers | Regression |
| E2E (manual) | `go install github.com/pablogore/shipwright@<tag>` from a clean `GOMODCACHE` | Slice 2 acceptance | Acceptance |

Coverage: `providers/go` inherits its own tests, run via the explicit
`go test` invocation above — not merged into root's `coverage.out`. This is a
correction, not the original plan: `go list ./...` was verified to return
exactly the 22 pre-extraction root packages in workspace mode, never
`providers/go` (see the corrected Open Question below), so the root
`make coverage` target's `go list ./...`-based package lists never included
`providers/go` and still don't. That is now a deliberate scope decision
(documented at the `Makefile` coverage section) rather than an oversight to
fix: `providers/go` is an independently published module (D2/D4) whose
coverage is not part of root's 90%/70% thresholds, which were calibrated
against the pre-extraction package set.

## Threat Matrix

`N/A` — no routing, shell command, subprocess, executable-file classification, or
process-integration boundary changes. The one adjacent surface is VCS
automation, and this design **deliberately avoids it**: tagging stays a manual,
reviewed step rather than a scripted push, precisely so no new automated
credential-bearing VCS path is introduced.

## Migration / Rollout

1. **Slice 1** (branch off `develop`): guards RED → module + `git mv` → three
   importer swaps → `go.work` → temp `replace` → delete `internal/capabilities/`
   → `COMPATIBILITY.md` line 46. Green under `go test -race ./...` **and**
   `(cd providers/go && go test -race ./...)` (the two invocations `./...`
   does not merge — see the corrected Open Question below) plus
   `GOWORK=off go build ./...`. Verify `git diff --stat -- pkg/shipwright/` is
   empty. Merge to `develop`.
2. **Tag interlude**: `git tag providers/go/v0.1.0 <merge sha>` +
   `git push origin providers/go/v0.1.0`. Confirm the proxy sees it
   (`GOPROXY=direct go list -m github.com/pablogore/shipwright/providers/go@v0.1.0`).
3. **Slice 2**: no-`replace` guard test RED → delete `replace` →
   `GOWORK=off go mod tidy` at root → `go install` acceptance from a clean
   `GOMODCACHE`.

Rollback boundary: slice 1 is atomic (`git revert -m 1`). Slice 2 reverts
independently back to the `replace` state. The published tag is the only
irreversible artifact — superseded by `v0.1.1`, never deleted.

## Open Questions

- [x] **CI `go mod download` / `go mod verify` under workspace mode, and
      whether `./...` spans `providers/go` in the `build`/`test`/`security`
      stages.** **Verified empirically in slice 1 — the originally designed
      answer was wrong on the second half.** `go list ./...` from repo root
      returns exactly the 22 pre-extraction packages, identically in
      `GOWORK=off` mode and in workspace mode; Go's `./...` wildcard **never**
      crosses a nested-module boundary declared via `go.work`'s `use` — only
      the `all` pattern or a fully-qualified import path does. `all` is not a
      safe drop-in substitute either, confirmed per-command: `go vet all`
      exits 1 (it also vets unrelated third-party dependency `_test.go`
      files with pre-existing vet issues, e.g. `google/go-cmp`,
      `prometheus/client_golang`); `go fmt all` explicitly refuses
      `providers/go` ("not formatting packages in dependency modules");
      `go list all` / `go test all` pull in the full ~400-package transitive
      dependency graph, not just the two workspace modules; `govulncheck`
      does not span `go.work` at all (root and `providers/go` scans produce
      disjoint findings). So the proposal's "CI unchanged" claim does **not**
      hold: before this fix, `providers/go` was silently excluded from every
      repo-wide `build`/`test`/`vet`/`fmt`/`govulncheck` invocation in both
      `Makefile` and `ci.yml`. **Fix applied**: one explicit
      `(cd providers/go && go <cmd> ./...)` (or module-scoped `govulncheck`)
      invocation added alongside each existing root one — not by widening
      `./...` to `all`, which the testing above showed is unsafe. Coverage
      (`go list ./... | grep -v ...`) is the one exception left unchanged by
      design, not oversight — see the Coverage note above.
      `go mod download`/`go mod verify` in the `setup` stage remain prefixed
      with `GOWORK=off` as originally designed; that half of the answer
      holds.
- [ ] **Repository visibility.** `git remote` confirms `github.com/pablogore/shipwright`,
      so the module path matches the repo and D4's premise holds. Not verified:
      whether the repo is public. If it is private, `go install …@latest` never
      worked and the whole D4 constraint is a pre-existing gap, not this change's
      regression — verify with
      `curl -s https://proxy.golang.org/github.com/pablogore/shipwright/@v/list`
      before slice 2 and report loudly if empty.
- [ ] **`go work sync` / `go.work.sum` churn** in the pre-commit hook
      (`go-mod-tidy`). Confirm the hook does not fight workspace mode; if it
      does, scope it with `GOWORK=off`.
